00伙伴赛道口径（这一页决定全场语气）

新增约束：「我参加的是伙伴赛道，需要淡化面向客户的使用内容」。所以这一版把重心从「游客玩得多爽」搬到「伙伴能拿到什么能力」。

一句话记住这版的口径 我们卖的不是「一个好玩的地图导览」，而是「让伙伴自己产出这类互动内容的一套平台」。
游客体验只作为产出物证明出现（20–30 秒，够证明它真能跑就行），其余时间全部给创作平台。

0.1 该说 / 不该说

✅ 要多说❌ 要淡化
主语 「我们给伙伴……」
「伙伴可以自己……」		 「游客会……」
「用户打开就……」（只在产出物示意时用 1–2 句）
能力 两套创作模板、AI 分段生成、可视化结构编辑、预览即真前台、一键发布 「沉浸感」「好玩」「上瘾」这类体验形容词当主线
证据 平台界面、模板差异、生成进度、结构图、发布包 长时间播放游客导览、逐站等语音念完
价值 伙伴的生产成本与上线速度；一次投入覆盖两种玩法 C 端获客、用户增长、社群运营
用词 伙伴、创作平台、模板、产能、交付、可复制 客户、粉丝、DAU、留存（除非评委先问）

0.2 时间怎么分配（重心已经挪过）

板块时长占比性质
开场定位0:4010%伙伴视角定位
第一轮 · 打卡（豫园）1:3021%互动示意 25s + 平台 30s + 从头生成 35s
第二轮 · 故事（红山动物园）2:3537%互动示意 30s + 平台 45s + 从头生成 80s

净结果：「面向游客的使用内容」两段合计只有 55 秒（13%），而平台与创作合计 3 分 50 秒（55%）——这才像一支伙伴赛道的作品。

为什么不能把游客段完全删掉 ppt-prompt.md 的演示顺序仍然是「互动后打开生成平台」。而且伙伴最关心的一个问题是「你这套东西产出的是什么」——所以每轮留 25–30 秒的产出物证明（长什么样、能不能跑），而不是「游客玩得多开心」。

01定位：给伙伴的互动引擎 + AI 辅助创作平台

开场 40 秒必须把这两层说清：引擎（产出物）和平台（伙伴怎么生产）。

1.1 三句话定位（照念）

第一句 · 引擎程导览是一个「景点内的互动引擎」，它决定伙伴的产出物长什么样、怎么玩。
第二句 · 平台它同时是提供给合作伙伴的「互动流程 AI 辅助创作平台」——伙伴自己生产内容，我们提供产能。
第三句 · 两种模式两套模板引擎目前支持打卡模式和故事模式，每个模式都有各自的创作模板——伙伴选模式，平台就给对应的生产流程。

1.2 谁是谁（一定要分清）

角色是谁在我们的故事里扮演什么
合作伙伴（我们的用户） 景区 / 文旅局 / 博物馆 / 园区 / 展会主办方 / 生态伙伴 主角。他们用创作平台生产内容，然后投放到自己的场地
游客（伙伴的客户） 到访的人，手机浏览器打开 配角。演示里只出现 20–30 秒，用来证明产出物真的能跑
最容易犯的错 一上讲台就进入「用户视角」讲导览体验——这是讲给 C 端评委听的。伙伴赛道的评委想看的是：这套平台给了伙伴什么能力、伙伴拿到之后能干什么、这件事能不能复制。

02两种模式 → 两套模板（全场最核心的一页）

在伙伴赛道里，「两种模式」不是两个玩法，而是两条可交付的生产线。

2.1 两种互动模式

维度打卡模式故事模式
一句话提供景区内沉浸式路线引导和打卡点背景讲解，走遍每个节点提供多条路线进行趣味互动，探索不同的路线
伙伴拿到的产出物一份带顺序的讲解清单 + 一条路线一张有入口、分叉、结局的关系图 + 多条路线
推进逻辑按节点顺序线性走完路口自己选，选择不可逆，单路径也要人点
适合的场地一条街、一个园区，有明确游览顺序逛不完的大园子、古镇、展会有「向左还是向右」
演示案例豫园 yuyuan红山动物园 attr-mvbsg4kw（故事《黑神话悟空》）

2.2 两套创作模板 —— 「平台」这个词的全部证据

两种模式在平台里是两个不同的编辑页、两套不同的提示词、两套不同的校验。这是可以当场演示、也经得起追问的差异化。

模板构成打卡创作模板故事创作模板
编辑页长什么样2 张卡：景点简介 + 节点内容4 张卡：故事结构 + 前情提要 + 节点内容 + 这个节点的去向
伙伴要填什么景点简介 + 每个节点的讲解故事名 + 前情提要 + 每站情节 + 每个去向的选项文案 + 结局标题
AI 写什么简介 1 段 + 每站 1 段（标题 / 要点 / 口播稿）结构 1 段 + 开场 1 段 + 每站 1 段
AI 的语气第三人称、导览口吻、讲清背景第二人称「你」、叙事口吻、情节要接住上一站的悬念
结构能力节点顺序＝游览顺序，无分叉可视化故事结构图；AI 可重排走向（节点与坐标不动）
发布门控全部节点写过文案才能发再加一条：结构无悬空、无孤立节点
可勾选的范围按节点逐段生成可逐项勾（故事名 / 前情提要 / 情节 / 选项文案 / 结局标题 / 改结构）
被问「模板到底指什么」的标准回答 「模板不是换皮肤，是一套完整的生产流程：编辑页结构 + AI 提示词 + 校验规则。打卡模板产出的是一份带顺序的讲解清单；故事模板产出的是一张有入口、分叉和结局的关系图，还要为每个岔路写选项文案。所以两者的编辑页、提示词、发布门控都不一样。」

2.3 三个记忆点

① 一个引擎，两种产出物

清单和关系图。同一份节点数据、同一套地图与语音，伙伴做一次投入覆盖两种玩法。

② 模式自带模板

每个模式都有自己的创作模板与提示词——伙伴选模式，平台就给对应的生产流程。

③ 伙伴自助，不改代码

输入名字 → 高德找地点 → 拖坐标 → AI 写 → 预览 → 发布。全程在浏览器里完成。

2.4 不要说的话

  • ❌ 不要把程导览讲成「一个给游客的 App」——伙伴才是我们的用户。
  • ❌ 不要说「AI 全自动」。AI 写叙事，坐标、结构边界、最终审核都是伙伴或我们的人。
  • ❌ 不要说「两种模式一键切换」——数据结构同构，但故事包要额外连分支、写选项。

03伙伴视角：这套平台能交付什么

这一页是伙伴赛道的「答案页」——评委在找的其实就这张表。

伙伴关心什么平台给什么演示里在哪一秒
我要多久能做出内容 AI 分段生成：简介 / 开场 / 逐站 / 选项一次跑完，写完立刻落盘 两轮「从头生成」
我的人会不会用 三步流程、两套模板、界面里没有一行代码 「生成平台」两段
我要做两种玩法，是不是要投两次 两种模式共用同一份节点数据（坐标 / 图片 / 讲解） 两轮模式的对照
我不满意 AI 写的怎么办 逐段可改、可按段重跑；结构可视化编辑；失败不覆盖原文案 故事模板 + 生成进度条
发出去的东西质量谁来兜底 发布门控：文案没写全 / 结构有悬空或孤立节点 → 按钮直接禁用并指路 模板段的一句带过
做好的东西怎么交付、怎么托管 发布包＝一个带版本号的 JSON + 图片目录，纯静态、可 CDN、可离线 「预览 → 发布」那一跳
以后换技术、接自己的系统难不难 播放端不依赖后端；讲解稿是纯文本，接自有 TTS / 小程序 / App 都是替换一层 收尾一句话（或留到问答）
这张表怎么用 不要念它。把它当成你 7 分钟里的「内容清单」——每一行都必须在演示里真的出现过一次；问答环节被问到任何一行，你都能立刻指回演示里的哪一秒。

04演示素材与准备

两轮六段，比单轮更容易乱。这一页就是「开演前照着点一遍」的清单。

4.1 四个演示对象

用途对象为什么是它给多少时间
产出物 A · 打卡 豫园 yuyuan 江南园林、节点少、走完快；产出物是「清单 + 路线」，用来对照故事。 25 秒（点自动 → 走一站就切）
产出物 B · 故事 红山动物园 attr-mvbsg4kw
故事《黑神话悟空》		 11 节点、入口猴山三岔、2 结局；产出物是「关系图 + 多条路线」，最有说明力。 30 秒（点开始 → 走一步 → 看结构）

4.2 演示前一天必须做完

  • 起本地服务（npm run dev），全程 localhost，不依赖外网部署。
  • 确认 .env：VITE_DEEPSEEK_*、VITE_AMAP_KEY、VITE_AMAP_SECURITY_CODE 全部有效。
  • 把两条「从头生成」路径各完整预跑两遍，确认检索秒回、节点正确、AI 有响应。
  • 把两份「已经生成好」的结果各自另存为草稿，作为 AI 超时时的切换目标。
  • 给两个草稿预置好检索缓存（高德结果已在草稿里），现场点检索不会卡。
  • 确认豫园草稿是打卡模式、红山草稿是故事模式（一旦反了，模板演示会错位）。
  • 录一段 3 分钟实机走查（故事模板 + 后台生成），本地 + 云盘各一份。
  • 准备离线自包含包一份（图片内联），作为断网兜底。
  • 浏览器：Chrome/Edge，1920×1080，缩放 100%，关通知、关 DevTools、指针调大。
  • 六个页面按顺序预开标签页：
    /tour/yuyuan → /publish/<豫园>/content → 新建（打卡）→ /tour/attr-mvbsg4kw → /publish/attr-mvbsg4kw/content → 新建（故事）
  • 提前点一次「开始」遮罩，确认中文语音能响（浏览器要求先有用户手势）。

4.3 已知限制（心里有数，别踩）

  • 地图安全密钥是明文配置，只适合演示；上线要改代理转发。被问「安全性」时主动说这条，是加分项。
  • 高德检索 citylimit: false，城市填错会命中外地同名景点——演示包已固定，不受影响。
  • 节点配图是外部图像工具生成后压到 800×450（约 30–43KB/张），不是实时生成，别声称「现场生成配图」。
  • AI 生成是分段串行：N 个节点＝1+N 次请求（故事勾结构再加 1 次）。11 节点完整生成不可能 60 秒跑完——见 07 节。

057 分钟演讲稿（可直接照念）

结构＝40 秒定位 + 两轮各三段 + 60 秒平台收束 + 75 秒伙伴价值与收尾。加重的是平台，游客段只有几十秒。

  1. 开场 · 伙伴视角定位0:00 – 0:40

    目标：40 秒把「引擎 + 平台 + 两种模式两套模板」说完，并明确我们服务谁。

    口播

    「大家好，这是程导览——一个景点内的互动引擎。」

    「它同时是给合作伙伴的一套 AI 辅助创作平台：我们的用户是伙伴，不是游客；伙伴用这套平台，自己就能把场地做成可互动的内容。」

    「引擎目前支持两种互动模式——打卡模式和故事模式，而且每个模式都有各自的创作模板。」

    「今天我用两个真实案例，各走一遍：先看产出物长什么样，再看平台怎么生成，最后从零生成一次。」

    🎬 切到 /tour/yuyuan（第一轮的产出物示意）。

  2. 第一轮 · 打卡模式（豫园）0:40 – 2:10

    三段式：① 产出物示意（25s）→ ② 打卡模板（30s）→ ③ 从头生成一次（35s）

    ① 产出物示意（25 秒，快）

    口播（配合操作）

    「这是豫园，打卡模式的产出物。伙伴做完之后，游客打开就是一张真实地图，左边是按顺序排好的节点。」

    「我点『自动』——」（点自动 → 开始）「——它会按顺序引导走完每个节点，到站自动播讲解。产出物就是这个：一条路线加一份讲解清单。」

    ⏱️ 不要等讲解念完。走一站、证明它能跑，立刻切。

    ② 打卡创作模板（30 秒）

    🎬 切到 /publish/<豫园草稿>/content。

    口播（配合操作）

    「切到创作平台。这就是打卡模式配套的创作模板——只有两张卡：景点简介和节点内容，每个节点写标题、要点和口播稿。」

    「注意它有多简单。待会儿你会看到故事模式的模板完全不是长这样。」

    ③ 从头生成一次（35 秒）

    口播（配合操作）

    「现在我从零做一遍。新建、输名字和城市、点检索——高德把关景区和周边地点都找出来了，勾几个当节点。」

    「下一步节点自动生成，坐标拖一下就准了。进内容创作，点 AI 生成——」（点）「它是分段跑的：先写简介，再一站一站写讲解，每段写完立刻落盘。」

    「跑完点预览、点发布——一条导览就交付了，全程没写一行文案。」

    ⏱️ 只用 35 秒，不要等全部生成完——见 07 节 的三段式降级。

  3. 第二轮 · 故事模式（红山动物园）2:10 – 4:45

    三段式同上，但每一段都换成故事形态——这一轮是全场重心，给足 2 分 35 秒。

    ① 产出物示意（30 秒）

    🎬 切到 /tour/attr-mvbsg4kw。

    口播（配合操作）

    「同一个引擎，第二种产出物。这是南京红山动物园，故事《黑神话悟空》，故事模式。」

    「点开始——」（点开始）「——地图上只有一个点。因为故事模式的产出物不是清单，是一张关系图：用户只能看见自己站在哪、下一步能去哪，走哪条路由他自己选。」

    「我点一个去向——」（点一个选项）「——小人沿真实路网走过去，情节换新。这就是伙伴拿到的第二种产出物：多条路线。」

    ⏱️ 30 秒，走到第二站就切走，别等结局结算。

    ② 故事创作模板（45 秒，本场最重要的 45 秒）

    🎬 切到 /publish/attr-mvbsg4kw/content。

    口播（配合操作）

    「切到创作平台。这就是故事模式配套的创作模板——四张卡，和打卡模板完全不同。」

    「最上面这张是故事结构图：入口在最左边，这里是分叉，右边虚线收口的是结局。点任何一个节点就能跳过去编辑它。」（点一个节点）

    「下面是前情提要——故事的开场，也是用户在开始遮罩里看到的那段。」

    「再下面是节点内容，和打卡一样写讲解；但故事模板多一张卡——这个节点的去向。」

    「每个去向要写一句选项文案，是用户点下去的那句话；结局还要写结局标题。这就是『每个模式各自的模板』：打卡模板只要写讲解，故事模板还要设计岔路和它的措辞。」

    ⏱️ 只点结构图上的一个节点做示范，不要动任何文案。

    ③ 从头生成一次（80 秒，全场高潮）

    口播（配合操作）

    「同样从零来一遍。名字、城市、检索、勾节点、拖坐标——」

    「进内容创作。故事模板这里多一个创作方向输入框，我写一句，比如『以寻找走失的同伴为主线，语气温柔』，然后点『AI 生成内容』。」

    「——它是三段式跑的：先设计走向，再写故事名和前情提要，最后一段一段写情节和路口选项。」

    「这里有个很关键的设计：写每一站的时候，会把上一站刚写好的旁白喂进提示词，所以情节是接得住的——不是每站各写各的。」

07「从头生成」怎么演示（全场最容易翻车的一段，而且要做两次）

矛盾在于：它是全片最有说服力的部分，也是唯一你控制不了耗时的部分——而且要重复两遍。

7.1 先说清真实耗时

模式请求次数大致耗时35s / 80s 够吗
打卡 4 个节点 1（简介）+ 4（节点）= 5 次 约 15–40 秒 勉强，必须节点少
故事 11 个节点 1（结构）+ 1（开场）+ 11（节点）= 13 次 约 40–120 秒 跑不完

7.2 推荐做法：三段式降级（诚实且可控）

  1. 现场真的跑前两段。让它真的执行 10–20 秒，看着进度条从「1/4」走到「2/4」——这是真的，不是演的。
  2. 把等待变成讲解。等的时候你正好在解释：「它是一段一段跑的，每段写完立刻落盘，所以某一段失败也不会覆盖你已经写好的内容。」——等待不是空白，等待是讲这套平台设计最好的时机。
  3. 到 15 秒还没跑到第三段，就切预跑结果。台词：「剩下的段我们已经预跑好了，直接看结果。」然后展示结构图 / 预览 / 发布。不解释、不道歉、不停顿。

7.3 让「两次从头生成」不显得重复的三个办法

  • 第一轮只走前半段。打卡那次只演示「检索 → 勾节点 → 下一步」，到 AI 点下去、进度条出现就切走，说「生成机制两轮一样，我们到故事模式看完整的一次」。
  • 把「不同点」放在第二轮讲。第一轮讲「平台能一键生成」；第二轮讲「故事模板还多一层：结构设计」。两次的解说词不能是同一套。
  • 第二轮才做完整闭环（预览 → 发布）。第一轮不演示发布，把「交付」这个动作留给最后一轮，收尾时观众印象里就是「从零到交付」。

7.4 备选做法（如果要「看起来真的从头跑完」）

  • 缩小案例。现场新建一个只有 3 个节点的小景点，1+3=4 次请求，能在一段话的时间里跑完。
  • 只勾一个部分。故事模式点「AI 生成内容」时会弹面板让你逐项勾（故事名 / 前情提要 / 情节 / 选项文案 / 结局标题 / 修改结构）。现场只勾「前情提要」，请求数变成 1 次，秒回；然后说「其余部分用预跑结果展示」。
  • 预置检索缓存。把「检索景区」提前跑过，结果留在草稿里——现场点检索是秒回的，不会卡在等网络。
四个绝对不要做的事 ❌ 不要在现场硬等 60 秒以上（而且你要等两次）。
❌ 不要说「我们平时很快，只是这里网络不好」（听起来像找借口）。
❌ 不要让两轮「从头生成」念同一套解说词（重复会显得内容单薄）。
❌ 不要跳过第二轮最后的「预览 → 发布」——那是「伙伴能自己交付」这个论点的唯一证据。
一句可以提前打的预防针 在第一次开始生成前说：「因为它是分段的，我会只跑前面几段给大家看节奏，剩下的用预跑结果。」——提前说清楚，切走的时候就不会显得像翻车。

095 分钟问答弹药库

先记三条通用原则。A（定位与赛道）和 C（伙伴落地）是伙伴赛道新增的重点，B（平台与模板）仍是最容易被追问的一组。

回答的三条通用原则

先结论，后支撑

第一句必须是答案本身，第二句才给理由。不要用铺垫开头。

不会就说不确定

「这个我们还没验证过，我的判断是……」评委最反感现编。诚实反而加分。

承认边界，给下一步

「现在只做到 X，Y 是下一步。」把边界说成路线图，而不是缺陷。

不要说的话（伙伴赛道专属提醒） ❌「我们是一个给游客的 App。」（客户是合作伙伴，说反了整段定位就塌了）
❌ 大篇幅讲 C 端体验、用户增长、社群运营——这轮的评委不是在看这个。
❌「AI 全自动，不需要人工。」（坐标校准、结构边界、内容审核都要人）
❌「我们已经有景区在用了。」（Demo 阶段没有真实伙伴，被追问就崩）
❌「两种模式一键切换、无缝互通。」（数据同构，但故事包要额外连分支、写选项）

A · 定位与赛道

A1一句话说，你们做的是什么？

两层：一个景点内的互动引擎，加上一个给合作伙伴的 AI 辅助创作平台。伙伴用它把自己的场地做成可互动的内容，游客在场地里边走边选。

A2你们和伙伴是什么关系？谁用你们的产品？

伙伴是我们的用户，游客是伙伴的用户。我们提供引擎和创作平台；伙伴提供场地、故事和最终审核；游客在伙伴的场地里玩。

为什么这么分：内容只有场地自己最懂，而且我们不可能替全国每个景点写文案——所以把生产能力交出去，比自己下场做内容更可扩展。

A3你们做的是 App 还是平台？

是平台，前台只是产出物的运行环境。游客打开的那个页面确实是我们的播放器，但它不是我们卖给谁的产品——它是伙伴产出的东西的展示形态。

A4为什么不直接做一个面向游客的导览 App？

因为那样每做一个景点都要我们自己写内容，做不动。伙伴赛道这件事的本质是：把产能交给别人，我们只做引擎和工具。

A5为什么要有两种模式？只做一种不行吗？

因为场地分两类，需求正好相反。有明确游览顺序的（一条街、一个园区）要的是走完——那是打卡模式；逛不完、天然有多条路的（大公园、古镇）要的是选择——那是故事模式。一套引擎覆盖两种场地，比做两个产品划算。

A6两种模式最本质的区别是什么？

打卡的产出物是清单，故事的产出物是关系图。打卡的真相是节点顺序；故事的真相是节点之间的关系——用户每次选择都会改变走的路线和看到的结局。

B · 平台与模板（高频追问）

B1「每个模式都有各自的创作模板」——模板到底是什么？

模板＝一个模式的完整生产流程，具体是「编辑页 + AI 提示词 + 校验规则」三件套。打卡模板是 2 张卡（景点简介 / 节点内容），AI 用第三人称导览口吻写；故事模板是 4 张卡（故事结构 / 前情提要 / 节点内容 / 去向），AI 用第二人称叙事写，还要给每个岔路写选项文案。

可展开：连发布门控都不同——打卡只要「所有节点写过文案」，故事还要求「结构无悬空、无孤立节点」。

B2你们的「模板」和市面上的 AI 写作模板有什么不同？

市面上的模板产出文本，我们的模板产出能跑的产品。模板写完不是给你一段文字，而是直接生成可发布的数据包（节点、坐标、结构、图片引用），前台立刻能玩。

B3伙伴需要什么能力？会不会很难上手？

会用浏览器就行。三步：确定范围（输名字城市、勾几个地点）→ 地图选点（拖一下坐标）→ 内容创作（点一次 AI，然后改不满意的地方）。

B4AI 生成的内容，伙伴能改吗？改完还能重跑吗？

能，而且是按段改、按段重跑。每一段（一个节点的情节、一个去向的选项文案）都能单独编辑；重跑也只跑你选中的那一段，不会覆盖别的部分。

B5如果 AI 写的结构不合理，伙伴能自己调吗？

能，结构是可视化编辑的。故事结构图上的节点可点选，去向可加可删，入口和结局都能改；AI 重排结构是可选项（默认不勾），勾了才会动。

C · 伙伴落地与交付（伙伴赛道重点）

C1一个伙伴从零开始，多久能做出第一条？

如果地点和节点已经确定，内容是分钟级的。现场演示里，从输入名字到发布跑完了一遍——真正花时间的是待办（AI 分段生成），而不是操作。

要诚实的地方：节点坐标的校准和内容审核还是人工，所以「第一条」的实际周期取决于伙伴准备得多快。

C2交付给伙伴的到底是什么？

一个发布包：带版本号的 JSON + 一组图片。纯静态、不依赖后端、可挂 CDN、可离线运行；也能接进伙伴自己的小程序、App 或公众号。

C3伙伴有几个景点，能批量管吗？

现在有统一的景点管理页，一行一个景点。每行能看到模式标、发布状态、节点数、已编辑/未编辑统计；删除可恢复。

还差的：多账号、权限、批量导入这些企业侧的行政能力，是我们下一步要补的。

C4怎么做一次可复制的落地？

三步：选一个场地 → 用平台产出一条 → 拿完成率说话。我们的目标是把「从零到上线」变成标准动作，而不是每个场地都是一次定制项目。

C5伙伴做两种玩法，是不是要投两次？

不用。两种模式共用同一份节点数据——坐标、图片、讲解都是同一份，只是推进逻辑和模板不同。伙伴做一次场地采集，两种玩法都能用。

C6同一个景点能不能同时挂两种模式？

引擎层面可以，产品层面要各自配一次。数据同构，所以素材不用准备两份；但故事模式需要额外连分支、写选项文案，所以不是「一键切换」。

D · 内容与 AI

D1AI 具体做什么？哪些是人做的？

AI 只写「叙事」，人定「地」和「界」。AI：故事名、前情提要、逐站情节、选项文案、结局标题，以及（可选）重排结构。人：景点与城市、节点与坐标、创作方向、最终审核。

D2大模型会胡编，事实错了怎么办？

两道闸：人审 + 「故事 ≠ 史实」的定位。故事模式写的是虚构/半虚构叙事；打卡模式的讲解会被喂入高德 POI 的真实地点信息（名称、类型、地址），发布前由伙伴逐节点确认。

可以坦白：目前没有自动事实核查，这是下一步要做的。

D3为什么不用大模型一次生成整份内容？

因为我们真的试过，然后出过事故。一次写 11 个节点 + 选项文案 + 结局标题会撞 max_tokens 被截断，模型只返回前 2 段，剩下的被兜底模板覆盖——把伙伴已经写好的文案覆盖成模板，是致命的。

可展开：现在改成「一段一次请求 + 写完立刻落盘 + 失败就整段不写回」。这是从真实 bug 里长出来的设计。

D4AI 写的东西会不会千篇一律？

会，如果只给关键词；不会，因为有两件事在起作用。① 伙伴可以填「创作方向」（主线、语气、意象）；② 写每一站时会拿到上一站刚写好的旁白，所以情节是接续的，不是每站独立生成。

D5生成成本是多少？

用的是轻量模型，单次导览的生成成本可以忽略。真正的成本在人工审核——所以我们把审核压缩成「只改不满意的那一段，重跑也只跑那一段」。

D6生成到一半断网会怎样？

已经写完的段落一个字都不会丢。每段跑完立刻落盘到本地草稿；失败的那一段保持原样不写回。播放端完全不依赖网络。

E · 技术与工程

E1技术栈是什么？为什么选它？

React + TypeScript + Vite + Tailwind，地图用高德 JS API 2.0，AI 接的是 DeepSeek。选型标准是「快」：TypeScript 保契约、Vite 保迭代、高德保地图与真实路网、轻量模型保生成成本。

E2两种模式的数据结构怎么统一的？

发布包是一个带版本号的 JSON + 图片目录，两种模式共用同一份节点数据。故事模式只是在包顶层多两个可选字段（mode、story）。

关键洞察：打卡其实是故事的特例——每个节点只有一个去向。所以底层只有一条「这个节点能去哪」的图函数，界面层才分成两个页面、两套模板。

E3地图和路网怎么做的？

全部走高德官方能力：POI 关键字搜索 + 周边搜索（找景点与周边地点）、行政区查询（城市/区域下拉）、步行路径规划（小人沿真实路网移动）。

可展开：检索串行 + 节流避免打爆配额；定位失败会落到主景点附近的兜底位置，不会全叠在一起。

E4最难的技术点是什么？

不是 AI，是「让 AI 只动该动的东西」。AI 可以重排故事结构，但节点和坐标一个都不能动；生成失败不能覆盖已有内容；结构写坏了前台要能降级成按顺序走、不白屏。这些边界才是真正花时间的地方。

E5怎么扩展？多城市、多景区、多伙伴？

播放端是纯静态的（一个 JSON + 图片），天然可 CDN、可无限扩展。生成端是唯一有状态的——把生成服务化、加上多租户，就是一个标准的 SaaS 后端。

E6数据从哪来？合法吗？

三层：高德 POI 提供地点事实，AI 提供叙事，伙伴提供最终审核。地图走官方 API、在授权范围内使用；配图是 AI 生成的原创图；文字是自己生成的。

F · 商业与合作

F1怎么赚钱？谁付钱？

伙伴付钱，游客免费。按场地/点位数订阅，或按项目定制。

为什么不是游客付钱：伙伴要的是停留时长和二次消费，不是从导览上收门票；让他们付费、游客免费，转化链条最短。

F2伙伴为什么买？能给他们带来什么？

三件事：更低的生产成本、更快的上线速度、一次投入覆盖两种玩法。过去做一套导览要找文案、配音、做小程序、雇人踩点；现在是一条流水线。

F3冷启动怎么做？第一批伙伴从哪来？

从一个「本来就没有导览」的场景切入。大景区已经有导览了，但大量小众公园、古镇、校园、园区、展会没有——预算低、要求快，正好是甜点。

抓手：先免费帮 1–3 个场地做一版，拿到「停留时长 / 完成率」对照数据，再谈付费。

F4怎么证明有效？

现在还没有真实伙伴数据，这是 Demo 阶段最诚实的状态。下一步就是做真实投放，拿「完成率」和「平均停留时长」去证明。产品里天然埋了这两个指标的位置。

F5如果高德/携程/大厂也做，你们怎么办？

大厂会做地图，不一定会做「叙事工具」。地图是入口，但把一个场地写成一段可玩的内容，是内容工种的问题。我们的壁垒是这条内容流水线和跑通它的领域知识。

F6你们的护城河到底是什么？

三件小事叠起来：① 两种模式共用一份数据（伙伴做一次投入覆盖两种玩法）；② AI 只动叙事、人定坐标（可用性的关键）；③ 生成 → 预览 → 发布是同一条链路（预览渲染的就是真前台）。

G · 压力问题（提前想好，别慌）

G1「这不就是加了个 AI 的语音导览吗？」

不是加了 AI，是换了机制，而且换了两层。对产出物，从「一条固定路线」变成「清单或关系图」；对伙伴，从「买一份内容」变成「买一套生产能力 + 两套模板」。

G2「故事模式是不是噱头？」

分支不是目的，「让用户想走完」才是目的。迷宫一样的园区、逛不完的古镇、展会——这些场地天生有「向左还是向右」，本来就该让人选。

如果被逼：承认「哪类场地最适合」还需要真实投放验证，这是下一步要测的第一件事。

G3「你们做了几周？能交付给伙伴吗？」

播放端已经能交付（纯静态、离线可用）；生成端要服务化才能多租户。我们会先服务化的就是生成接口，其余是工程收尾。

G4「如果没有 AI，你这个产品还成立吗？」

成立，但会慢十倍。互动引擎、迷雾地图、真实路网、分支推进都不依赖 AI；AI 解决的是内容生产的成本，没有它产品依然能跑，只是伙伴的生产效率回到人工时代。

G5「内容质量怎么保证？」

发布前必须过两道门：① 所有节点都写过文案才能发；② 故事结构必须无悬空、无孤立节点，否则发布按钮直接禁用并指出是哪一条。

G6「为什么不做 AR / VR？」

因为我们要的是「现场走」，不是「戴上设备」。VR/AR 把用户从真实环境里剥离；而手机浏览器就够——对伙伴来说也意味着零推广成本和零硬件门槛。

H · 团队与下一步

H1团队怎么分工？

按你们真实的分工回答。不要编造团队规模；小而全的团队在黑客松里是加分项。

H2下一步最重要的一件事？

找一个真实场地做一次投放，拿到「完成率 / 停留时长」的对照数据。在此之前，所有关于「互动更好」的说法都只是我们的判断。

配套三件事：① 生成端服务化（多租户）；② 企业侧的管理能力（多账号、权限、批量）；③ 内容审核工具（现在是手工审核）。

H3如果给你一笔钱，最先花在哪？

花在「拿到真实数据」上，不是花在功能上。先做 3–5 个真实场地的内容投放与埋点，用数据决定接下来做企业能力、做移动端、还是做第三种模式。
