## 0. 一句话

打卡模式的内容创作页**原样保留**；故事模式另起一页，以**故事结构**（入口 / 分叉 / 结局）为中心——上面是能看能点的结构图，下面是当前节点的文案与去向文案，AI 一次把讲解和选项文案都写了。两页共用同一份草稿、同一个路由。

## 3. 方案对比

### 3.1 分页方式

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **a（推荐）** | 路由不变，`/publish/:id/content` 里按 `draft.mode` 选组件（分发层照抄 [TourRoute.tsx:58](file:///D:/Users/qmruan/Desktop/item/tour-hub/src/pages/TourRoute.tsx#L58)） | 一个入口文件 + 两个组件 | 与前台「同一个 `/tour/:id` 按 mode 分发」同构；所有跳转链接（阶段二、列表、`?spot=` 定位）一个字都不用改；作者改模式后自动换页 |
| b | 两个路由：`/content`（打卡）/ `/story`（故事） | 多处入口链接要判断 mode，旧链接会 404 | 路由语义直白，但收益不值这些改动 |
| c | 一页加「打卡 / 故事」页签 | 与阶段一的模式开关重复，两处都能改模式 | 同一个东西两个开关，最容易漂移，不建议 |

### 3.2 故事页的信息架构

| 方案 | 做法 | 评价 |
|---|---|---|
| **a（推荐）** | 左栏节点列表照旧；右栏自上而下：结构图 → 节点内容 → 这个节点的去向 | 沿用作者已记住的「左选节点、右写内容」；宽屏资源给到最需要的图与文案；改动量最小 |
| b | 三栏（列表 / 内容 / 结构） | 1440 以下就挤，且结构图天生要横向空间 |
| c | 图打底 + 浮层写文案（像阶段二地图那样） | 故事页没有地图，把写作动作复杂化；这条留给 doc-02 的 T4（地图连线） |

### 3.3 结构图怎么画

| 方案 | 做法 | 评价 |
|---|---|---|
| **a（推荐）** | 横向分层 SVG：按「从入口走几步」分列，节点是小胶囊 + 名字，边是折线；入口描边加重、结局圆角收口、**当前节点实心高亮**；点胶囊 = 选中该节点 | 与「入口在左、故事向右走」的直觉一致；宽 ~768 × 高 ~200 装得下 11 个节点；按 `storyNextChoices()` 的**生效去向**画，所以「没连过 = 按数组顺序接下一个」也照实画出来 |
| b | 竖向缩进树（`├ └` 目录） | 实现最省，但共用尾巴会被重复打印（红山那种"三岔汇入一条长链"会膨胀成十几行），且不像图 |
| c | 力导向 / 环形 | 迷宫感、每次进页面排版都不一样，不做 |

### 3.4 AI 写选项（`label` / `note` / 结局标题）

| 方案 | 做法 | 评价 |
|---|---|---|
| **a（推荐）** | 扩 `fillSpotContent()`：故事包的输入带上「每个节点的去向（目标名）」与「谁是结局」，让模型在同一个 JSON 里多返回 `choices: [{ label, note }]`（按去向顺序一一对应）与 `endingTitle`；**一个按钮一次写全** | 作者点一次就对；复用现成的截断修复（`extractJson`）与模板兜底；风险是 prompt 变长 → 用"先讲解、后选项"的分组输出压住 |
| b | 故事页多一个「AI 写选项文案」按钮 | 只补选项、重跑便宜；但作者要记得点两次 |
| c | 完全分开（讲解 / 选项两个按钮，互不覆盖） | 最可控，但按钮变多、两条 prompt 都要维护 |

### 3.5 去向（关系）要不要能在这页改

| 方案 | 做法 | 评价 |
|---|---|---|
| **a（推荐）** | 「这个节点的去向」卡里能**加 / 删去向、设为入口、标为结局**（等价于阶段二那张分支卡），阶段二那套原样保留 | 写作时最烦"少连一条线 → 跳回阶段二 → 再回来"；两边写的是同一份 `draft.story`，不存在第二份真相 |
| b | 保持现状：这页只写字，关系只能去「调整地点」连 | 改动为零，但故事页永远只是"半个编辑页" |

### 9.8 事故：本地草稿被写坏，从浏览器 LevelDB 捞回（2026-10-17 同日）

## 10. 故事页 AI 改为分段跑 + 真实进度条（2026-10-17 同日）

用户标注（那条忙时 toast 上）：「**最好在此处输出生成进度**」。选项问答选了「**拆成多次请求，按段推进**」（没选「真实阶段 + 计时」「按时间推演的百分比」「改流式」）。

### 10.1 拆成三种段

故事页原来一次 POST 写完故事名 + 前情提要 + 全部节点情节 + 选项文案 + 结局标题，跑的时候界面只有一句「AI 正在…」，而且一次写到 8192 token 上限还有被截断的风险。现在按段拆：

| 段 | 入口函数 | 产出 |
|---|---|---|
| 结构（**只有勾了「修改故事结构」才跑**） | `fillStoryStructure(input)` | `entry` + 每节点 `to`，节点名要对得上，**截断即整段作废** |
| 故事名 + 前情提要（开场） | `fillStoryIntro(input)` | `title` / `description` |
| 每个节点一段（**有几个节点就几次**） | `fillStoryNode(input, index, previous?)` | 该节点的 `poetic` / `slides[0]` / `choices` / `endingTitle` |

- `aiDraft.ts` 里删掉了合并版 `storySystemPrompt()`，换成 `storyStructureSystemPrompt()` / `storyIntroSystemPrompt()` / `storyNodeSystemPrompt(count, index)` 三段提示词，加了一个共用的 `callModel(system, user, key?)`（返回 `{ parsed, truncated }`）。`extractJson(text, key?)` 的 key 改成可选 —— 开场那段是个没有数组字段的对象，取不到数组没法用截断修复。
- `FillContentInput` 收回成打卡专用（`{ name, description, city?, amapContext?, spots }`），故事侧另开 `StoryFields`。**打卡页 `fillSpotContent()` 一行没动**，仍是「一次请求写完讲解 + 简介」。
- **上一段喂下一段**：`fillStoryNode` 的 user message 里带上「上一站刚讲完」＝`spots[index-1].slides[0].narration`（已经在写这一站时落过盘的那版）。所以「情节前后相接」是被喂进去的，不再指望模型自己记得上一段。

### 10.2 进度怎么显示

- 页面里把这一趟要做的事拼成一个 `steps` 数组，**串行**跑；每段跑完立刻 `working = persist(...)` 落盘（中途刷新 / 关页面，已经写完的段不会丢），失败的那段不改动原文案、记进 `failures`，最后合成一条 toast（全失败则明说「AI 未接通（…），这一趟什么都没写，原内容没动」）。
- 忙时 toast 变成 `[进度条] [3/4] AI 正在写「乙地」`：进度条 **实心 = 已跑完的段 `(done-1)/total`**，**浅色 = 正在跑的这段 `1/total`**（所以最后一段还在跑时整条才是满的，不会提前显示 100%）；右边 `3/4` 是步骤计数。
- 忙时**不显示「关闭」按钮**——进度得留在屏幕上；跑完 / 失败后按钮回来。
- 代价：总请求数从 1 次变成 `1 + N` 次（勾结构再加 1），总时长比原来一次调用长，换来的是真实进度、逐段落盘、以及每段 max_tokens 压力小得多。

## 11. 一次真实事故的复盘：「AI 只返回了 2/11 段，其余用模板补齐」（2026-10-17 同日）

用户在真实草稿 `attr-mvbsg4kw`（11 节点）上标注了那条 toast，让「顺便看看这个问题」。

**这条 toast 出自 §10 之前的旧链路**：`AI 只返回了 N/M 段，其余用模板补齐` 这句现在只剩**打卡页**的 `fillSpotContent()` 在用（`aiDraft.ts` 里那一句 `notes.push`）；故事页改成分段后不可能再产生这句话。草稿的 `updatedAt` 是 **15:07:20**，而分段改造落盘是 15:11 —— 也就是那次点击跑的是**改之前的一次性链路**。

**为什么只有 2/11**：一次 POST 里让模型写 11 个节点的 poetic + 要点 + 旁白 + 每个去向的选项文案 + 结局标题，超过 `max_tokens: 8192` → 响应被截断 → `extractJson()` 的截断修复从后往前切、只把**已经写完整的前 2 段**救回来（落下来的正是**猴山、新狼馆**这两个头节点）→ 其余 9 段走 `templateContent()` 兜底。

**真正的伤害是「兜底内容被写回草稿」**：旧链路里页面把 `contents` 全量写回（`ContentCheckinPage.tsx` 与旧故事页都是），所以那 9 个节点被模板覆盖成了：

- `poetic` = 「红山动物园 · 第 N 站」，`slides[0].title` = 纯地点名
- `bullets` = 「<简介前 36 字> / 可结合高德地点信息完善讲解 / 地图上可拖动校准坐标」
- `narration` = 「你来到<节点名>，停下脚步。这一段情节还没有人写——先记下这一站，回头补上。」
- 选项文案 9 条变成「前往 <节点名>」；3 个结局节点的 `endings` 变成「结局 · <节点名>」

（那一次勾了「修改故事结构」，所以 `story.choices` 被整体换成重排后的显式去向 —— 这一部分是**用户要的**，不算伤害：线性那条从「狼馆 → 本土区（数组顺序）」变成「狼馆 → 细尾獴馆」这种每个节点都落显式去向的写法。）

**§10 的分段改造已经堵掉这个坑**：每个节点一次小请求，撞不到 `max_tokens`；而且**某段失败就整段不写回、保留原文案**（`ContentStoryPage.tsx` 里 `if (r.source === 'mock') return r.reason`）。只勾「情节」跑失败也不会再拿模板文本盖掉已有内容。

**还留在打卡页的同一个坑**（用户当日选了「**打卡也改成按节点跑**」，已改，见 §12）：`fillSpotContent()` 原先是「一次请求写全部 + 没返回的段用模板写回」（`ContentCheckinPage.tsx` 把 `result.contents[i]` 无差别铺回去），节点一多就会重演。

**文案可恢复**：`public/spots/attr-mvbsg4kw.json`（13:43 那版发布包，早于 15:07）里这 9 段的 `poetic` / `bullets` / `narration` 完好（如「本土物种保育区离猴山不过百米，却是另一种安静…」），`endings` 里也留着 2 个真标题（「结局 · 抱着树干的午后」「结局 · 与虎隔林相望」）。也就是说这 9 段的损失是**可逆的**：要么从发布包补回文案（结构与坐标不动），要么用现在的分段链路只重跑「情节 / 选项文案 / 结局标题」。（用户当日回「**不需要，我自己重跑**」，所以这一条不做了。）

## 12. 打卡页也改成按节点跑（2026-10-17 同日）

承接 §11：用户回「**A. 打卡也改成按节点跑**」（B 的文案恢复不需要，他自己重跑）。

### 12.1 拆法（与故事侧对齐）

`aiDraft.ts` 里删掉了 `fillSpotContent()`（它的「一次写全部 + 缺的用模板补齐」正是 §11 那次事故的成因），换成与故事侧同构的两段：

| 段 | 入口函数 | 产出 |
|---|---|---|
| 简介 | `fillCheckinIntro(input)` | `description`（列表与封面用） |
| 每个节点一段（**有几个节点就几次**） | `fillCheckinNode(input, index)` | 该节点的 `poetic` / `slides[0]` |

- 提示词由 `checkinSystemPrompt(count)` 拆成 `checkinIntroSystemPrompt()` 与 `checkinNodeSystemPrompt(count, index)`；两段共用 `checkinBrief()` / `checkinNodeList()`，节点段的 user message 里带**已经定好的简介**（跟故事页把「前情提要」喂给节点段是一个用法）＋全节点清单并标出「← 就是这一站」，让讲解知道自己在第几站。
- 类型：`FillContentInput` / `FillContentResult` 删掉，打卡侧改叫 `CheckinFields`（与 `StoryFields` 对称）；结果是 `CheckinIntroResult` / `CheckinNodeResult`。打卡节点段没有去向，所以 `choices` / `endingTitle` 走 `toContent(..., story=false)` 自然为空。
- **打卡页不再用模板覆盖原文案**：某一段失败（`source === 'mock'`）就整段不写，原文案保留 —— 与故事页口径一致。代价是「没配 key 时点一下会什么都不写」（旧行为是拿模板铺一个骨架给你改），换来的是**不会再出现 §11 那种覆盖**。

### 12.2 进度条抽成共用组件

两页的底部 toast 长得一模一样（`[进度条] 3/4 AI 正在写「乙地」`），抽成 `src/components/GenProgressToast.tsx`（props：`text` / `progress` / `busy` / `onClose`），故事页与打卡页都用它 —— 以后改一处两边一起变。进度口径与 §10.2 一致：**实心＝已跑完的段 `(done-1)/total`、浅色＝正在跑的这段 `1/total`**，忙时不给「关闭」。
